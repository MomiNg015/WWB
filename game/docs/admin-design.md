# 管理后台设计方案

状态：首版后台已实现。React / TypeScript / Express / Socket.IO 工程，使用 SQLite；管理入口 `/admin`，接口前缀 `/api/admin`。管理员初始用户名为 `moming`，临时密码按用户在对话中指定的值初始化，服务端只保存 scrypt 哈希。后台采用独立管理界面，不复用游戏画布。

已完成：管理员登录/退出/改密、角色权限；用户新增/查询/修改/封禁/归档；物品与角色草稿CRUD；素材上传；规则配置；发布预检与测试局、版本发布/回滚；在线房间关闭、已结束对局查询、审计日志；数据库迁移与备份。操作说明见 admin-guide.md。

后续扩展：角色战斗技能与全新模式、批量编辑/导入、完整长期对局回放、管理员多级审批。当前角色仅提供外观，不给经典模式增加属性优势。测试用户没有单独的玩家用户名/密码登录体系，玩家仍沿用原游戏匿名身份。

## 1. 数据边界

原先 Session 存储在 sessions.json；现在启动时一次性导入 SQLite 并保留用户ID、登录凭证、积分和场次。物品基础数据从静态JSON初始化为可编辑草稿。已新增独立管理员认证、角色模板和内容发布版本；房间及正在进行的对局仍在内存中。

账号资料、角色模板、物品定义和对局状态分开存储。游戏中的 HP/MP/CP 和临时手牌属于单局状态，不能直接当成账号资产；经典模式不增加永久背包或角色属性优势。

## 2. 页面结构

| 页面 | 管理内容 | 主要操作 |
| --- | --- | --- |
| 总览 | 用户数、在线人数、进行中对局、待发布变更、近期异常 | 跳转对应记录，不堆砌无实际数据的图表 |
| 用户 | ID、昵称、状态、积分、场次、创建/最近活跃时间 | 搜索、筛选、新增测试用户、修改昵称、封禁/解封、积分调整、归档 |
| 用户详情 | 基本资料、角色关联、积分流水、对局记录、管理记录 | 分页查看；修改注明原因；凭证不展示、不提供编辑 |
| 物品 | 稳定ID、名称、分类、属性、攻防、MP消耗、价格、抽取权重、能力、状态、版本 | 新建、复制为新物品、编辑草稿、预览、停用、删除未使用草稿 |
| 角色 | 角色模板、形象、说明、可用模式、被动能力、版本 | 增删改查、预览、启停；与玩家账号、守护神分开 |
| 游戏配置 | 守护神、灾祸、超常现象、模式、初始资源与上限、抽取池 | 按类型编辑；经典配置保留基线；新玩法建立独立模式 |
| 房间与对局 | 房间状态、参与者、配置版本、开始/结束时间、结果 | 查看、检索、关闭异常房间；强制结束必须记录原因和计分处理 |
| 发布管理 | 草稿、差异、检查结果、发布历史 | 预检、测试局、发布、回滚 |
| 审计与权限 | 管理员、角色权限、操作日志 | 授权、撤销、过滤审计记录 |

用户管理不提供任意填写 token、密码或正在进行对局的 HP。封禁需检查登录、加入房间和提交行动；对已连接用户同步撤销可操作会话，进行中的对局按明确退出规则结算。

## 3. 页面交互

桌面端采用固定左侧导航、顶部面包屑、主要内容区。列表页依次为标题/新增按钮、搜索与筛选、表格、分页。以数据密度和操作效率为主，不沿用游戏的固定画布。

简单字段在详情抽屉编辑；物品和角色采用独立编辑页。物品页分为基本资料、战斗数值、能力配置、素材与文案，右侧展示真实游戏卡牌预览和校验结果。图片只支持受控上传类型和大小，名称与图片路径解耦；修改名称或素材不改变物品ID。

每次操作呈现加载、成功、字段错误、服务错误、无权限、空数据等状态。表单保留失败时的输入；离开未保存草稿时提醒。批量操作明确勾选数量和作用范围，不把当前页选择误当成全库选择。

禁用操作显示原因。例如“已被版本 v3 引用，请停用或创建新版本”，不能只显示灰色按钮。删除、封禁、积分调整、发布前展示对象、数量、修改差异和生效范围。

## 4. 物品与能力编辑

能力由服务器注册表定义，例如伤害、恢复、反射、添加灾祸；后台根据能力参数 schema 自动生成表单。管理员可以选择已有能力并配置参数，不能上传任意 JavaScript 或执行代码。

新增物品可复用已实现能力；全新机制仍需开发引擎处理器、动画事件和测试，再注册到后台。字段按类别显示：无MP消耗的物品不展示奇迹消耗输入，不支持的组合给出明确校验。

预检包括数值范围、引用存在性、分类与能力兼容、权重非负且抽取池非空、素材存在、多语言回退、循环引用及引擎支持情况。预览只说明展示效果，测试局用于验证实际规则。

## 5. 角色设计

区分 User（账号）、CharacterDefinition（角色模板）、UserCharacter（玩家拥有/选择的角色）、MatchPlayer（单局玩家）。角色模板包含稳定ID、名称、头像/立绘、描述、可用模式、能力引用和配置版本。

默认经典模式中角色仅影响外观；HP/MP/CP仍由模式规则统一决定。若新玩法允许角色属性或被动技能，只对明确启用该机制的模式生效。守护神继续作为独立战斗内容管理，不与可选角色混合。

## 6. 保存、发布与对局一致性

游戏内容采用“草稿 → 预检 → 测试局 → 发布”。保存不等于对玩家生效；发布包包含物品、角色、抽取池和规则的完整版本，不能部分成功。

新对局绑定一个不可变内容版本。引擎通过该版本的目录查询物品，不再直接读取可变全局 catalog；机器人、卡面预览、合法性判断、抽牌和效果计算使用同一目录。客户端携带并验证版本，旧对局不会因管理员改攻防或停用道具而中途改变。

回滚改变新对局采用的版本，不覆盖历史版本，也不逆转已经发生的账号积分操作。积分纠错使用新的补偿流水。

账号资料变更、封禁与内容发布分开：账号操作按权限即时生效，积分调整与对局结算通过数据库事务和幂等标识避免覆盖。编辑表单带记录版本号，提交旧版本返回冲突及差异，不静默覆盖另一位管理员。

## 7. 删除策略与审计

无引用草稿可以删除。已发布物品和角色使用停用/归档，保留历史对局引用；停用只影响后续发布的配置。用户默认归档，删除测试账号前检查关联。彻底清除用户数据另设明确流程，不通过普通列表删除按钮执行。

每次写入记录管理员、时间、对象ID、操作类型、原因、修改前后差异、请求ID和结果；审计记录不能由普通内容管理员编辑。敏感凭证不进入审计正文。

## 8. 权限

| 角色 | 默认权限 |
| --- | --- |
| 超级管理员 | 管理员与权限、所有管理模块 |
| 用户管理员 | 用户资料、封禁与授权范围内的积分调整 |
| 内容编辑 | 物品、角色、模式草稿与测试局 |
| 发布管理员 | 内容预检、发布、回滚 |
| 只读审计员 | 脱敏查询、历史、审计 |

权限落实到服务端接口和具体操作。管理员采用独立登录与会话，不能把游戏匿名会话当作管理员身份；首次启动创建用户指定的初始管理员，也可通过初始化环境变量覆盖。没有公开注册管理员入口。Cookie会话使用HttpOnly与SameSite，写接口校验来源/CSRF，登录失败有限流；修改密码或权限会撤销相关会话。

## 9. 存储与接口

建议的数据实体：users、admin_users、admin_roles、admin_role_permissions、rating_ledger、item_definitions、item_revisions、character_definitions、character_revisions、user_characters、ruleset_revisions、content_releases、matches、match_players、audit_logs、assets。

首版SQLite实际表为 users、administrators、admin_sessions、records、releases、audit、matches、metadata。records按类型存储物品、角色、规则及修订号；releases保存完整不可变快照；权限为服务端固定角色映射，积分调整记录在审计中。尚未拆成上述全部逻辑实体表，列表在服务端过滤并分页返回，当前按单进程运行设计。

事务数据库作为权威数据源。现有 sessions.json 编写一次性导入，保留用户ID和积分；旧登录凭证通过明确迁移或重新签发处理。后台列表从数据库分页查询，不把全体用户和凭证下发浏览器。

接口示例：GET/POST /api/admin/users，GET/PATCH /api/admin/users/:id，POST /api/admin/users/:id/rating-adjustments，POST /api/admin/users/:id/suspensions；物品/角色提供列表、详情、草稿编辑、复制、归档；发布提供 validate、publish、rollback 操作。浏览器只提交意图，服务器校验并写审计。

## 10. 实施与验收顺序

1. 数据库、身份迁移、管理员认证、权限、审计、用户查询和编辑。
2. 物品管理、素材上传、能力参数表单、草稿与内容版本；改造引擎按版本查询目录。
3. 发布、回滚和受控测试局；验证旧对局不受新版本影响。
4. 角色模板与模式扩展；新增对局历史、房间管理和概览统计。

关键验收：普通用户无法调用任何管理写接口；越权修改失败；审计与数据原子写入；并发修改可发现冲突；非法配置无法发布；零权重池被拒绝；发布/回滚不改变进行中的对局；删除不破坏历史；积分调整与比赛结算无丢失更新；备份可恢复。
